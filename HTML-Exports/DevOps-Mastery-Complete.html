Linux — Interview Questions & Answers

Basic / Mid-Level

Q1: What is the difference between a hard link and a soft link? > Hard link: Another directory entry pointing to the same inode. Cannot span filesystems. Deleting original doesn’t remove data until all hard links deleted. > Soft link (symlink): Points to a path/name. Can span filesystems. Breaks if target is deleted. > ln file hardlink vs ln -s file softlink

Q2: Explain the Linux boot process. > 1. BIOS/UEFI POST → finds bootable device > 2. MBR/GPT → loads bootloader (GRUB2) > 3. GRUB2 → loads kernel image + initramfs into memory > 4. Kernel initializes hardware, mounts initramfs (temporary root FS) > 5. Kernel mounts real root FS, starts /sbin/init (systemd on modern distros) > 6. Systemd reads /etc/systemd/system/, starts default target (multi-user.target or graphical.target) > 7. Login prompt

Q3: What is the difference between ps aux and ps -ef? > Both show all processes. aux is BSD style (shows %CPU, %MEM, VSZ, RSS). -ef is POSIX style. ps aux additionally shows non-tty processes.

Q4: How do you find which process is listening on port 8080?

ss -tlnp | grep :8080
lsof -i :8080
fuser 8080/tcp

Q5: What is a zombie process? How do you remove it? > A process that has finished execution but its parent hasn’t called wait() to collect its exit status. It holds a PID and entry in the process table. Kill the parent process to clean up zombies (they’ll be re-parented to init which will reap them).

Q6: What is nice and renice? > nice sets the priority when starting a process (-20 = highest, 19 = lowest, default 0). > renice changes the nice value of a running process.

nice -n 10 make -j4
renice -n -5 -p 1234    # requires root for negative values

Q7: Explain cron syntax.

*  *  *  *  *  command
│  │  │  │  └─ Day of week (0-7, Sun=0)
│  │  │  └──── Month (1-12)
│  │  └─────── Day of month (1-31)
│  └────────── Hour (0-23)
└───────────── Minute (0-59)

0 2 * * 0 /scripts/backup.sh    # Every Sunday at 2am
*/15 * * * * /scripts/health.sh # Every 15 minutes
@reboot /scripts/startup.sh     # At boot

Q8: What is the difference between > and >>? > > overwrites the file. >> appends to the file. > 2> redirects stderr. 2>&1 redirects stderr to stdout. &> redirects both.

Q9: How do you check disk usage?

df -h           # filesystem usage
du -sh /var/log # directory size
du -h --max-depth=1 /var  # one level deep
ncdu /var       # interactive (if installed)

Q10: What are environment variables and how are they set?

export VAR=value          # current shell + children
echo $VAR
env                       # view all
unset VAR                 # remove
printenv HOME
# Persistent: add export to ~/.bashrc, ~/.bash_profile, /etc/environment

Advanced / Senior Level

Q11: Explain Linux namespaces and how Docker uses them. > Linux namespaces provide process isolation by limiting what a process can see. Docker uses: > - PID namespace: Container processes see only their own PID space (PID 1 in container ≠ PID 1 on host) > - NET namespace: Container gets its own network stack (eth0, lo, routing table) > - MNT namespace: Container sees only its own mount tree > - UTS namespace: Container can have its own hostname > - IPC namespace: Isolated IPC resources > - USER namespace: (optional) Map container root to non-root host user

Q12: What are cgroups and how do they relate to containers? > Control groups limit and account for resource usage of process groups. Docker uses cgroups to: > - Limit CPU (--cpus=2), memory (--memory=512m) > - Limit disk I/O bandwidth > - Track resource consumption per container > docker run --cpus=1.5 --memory=1g nginx

Q13: How does iptables work? How does Docker manage iptables? > iptables works with kernel netfilter hooks. Packets go through chains (INPUT, OUTPUT, FORWARD, PREROUTING, POSTROUTING). Docker: > - Creates DOCKER chain in FORWARD and nat tables > - Adds DNAT rules in PREROUTING for port mappings > - Sets FORWARD default to DROP but allows docker network traffic > - Sets masquerade (SNAT) in POSTROUTING for outbound container traffic

Q14: What is the difference between soft and hard limits (ulimit)? > Soft limit: Current effective limit; can be raised up to hard limit by the user. > Hard limit: Maximum that unprivileged users can set; only root can raise it.

ulimit -a              # show all limits
ulimit -n 65535        # set open files (soft)
ulimit -Hn 65535       # set open files (hard, root only)
# Persistent: /etc/security/limits.conf
* soft nofile 65535
* hard nofile 65535

Q15: Explain strace. When do you use it? > strace traces system calls made by a process. Used for debugging crashes, permission issues, file not found errors.

strace -p PID                    # attach to running process
strace -e trace=open,read ls     # filter specific syscalls
strace -o /tmp/trace.log -f cmd  # follow forks, log to file
strace -c program                # summary of syscalls + timing

Q16: A server is running out of memory but free -h shows available memory. What could be wrong? > - Swap exhaustion: Check swapon -s or vmstat > - OOM killer invoked: Check dmesg | grep -i oom > - Memory leaks in application: Check pmap -x PID | tail -1 > - File descriptor exhaustion: Check ulimit -n and /proc/PID/fd > - Kernel memory (slab): Check slabtop or /proc/slabinfo > - Dirty page writeback: cat /proc/meminfo | grep Dirty

Q17: How do you debug a “Too many open files” error?

# Check limits
ulimit -n
cat /proc/sys/fs/file-max    # system-wide max

# Check current usage
lsof | wc -l                 # total open files
lsof -p PID | wc -l          # per process
ls /proc/PID/fd | wc -l      # directly

# Check system-wide
cat /proc/sys/fs/file-nr     # used / free / max

# Fix
ulimit -n 65535              # temporarily
echo "* soft nofile 65535" >> /etc/security/limits.conf
echo "* hard nofile 65535" >> /etc/security/limits.conf

Q18: Explain the difference between /proc and /sys. > /proc: Process information + kernel interfaces. Contains a directory per PID. Also has system info: /proc/cpuinfo, /proc/meminfo, /proc/net/. > /sys (sysfs): Structured view of kernel devices and drivers. Used to modify kernel parameters at runtime. More organized than /proc.

Q19: What is a segmentation fault? How do you debug it? > SIGSEGV — process tried to access memory it doesn’t have permission to (null pointer, stack overflow, buffer overflow).

# Enable core dumps

Networking — Interview Questions & Answers

Q1: What happens when you type https://google.com in a browser? > 1. Browser checks cache (DNS cache, HTTP cache) > 2. DNS resolution: OS → /etc/hosts → resolv.conf → recursive resolver → root NS → .com NS → google.com NS → A record > 3. TCP 3-way handshake to port 443 > 4. TLS handshake: ClientHello → ServerHello + Cert → Key exchange → session key → Finished > 5. HTTP/2 GET request with headers (Host, User-Agent, Accept, Cookie, etc.) > 6. Server processes request, response traverses CDN/LB/app servers > 7. Browser renders HTML, parallel requests for CSS/JS/images > 8. Service worker may intercept if PWA

Q2: What is the difference between NAT and PAT? > NAT (Network Address Translation): Maps private IP to public IP (1:1 mapping) > PAT (Port Address Translation) / NAPT: Many private IPs share one public IP using different source ports (many:1 mapping) — what home routers do

Q3: Explain BGP vs OSPF. > OSPF: Interior Gateway Protocol (IGP). Used within an organization. Link-state routing, builds complete topology map, uses Dijkstra algorithm. Fast convergence. > BGP: Exterior Gateway Protocol (EGP). Used between Autonomous Systems (internet routing). Path-vector protocol. Policy-based routing. Used by cloud providers and ISPs.

Q4: What is a VLAN and why is it used? > Virtual LAN logically segments a physical network. Benefits: security isolation, broadcast domain reduction, simplified management. Layer 2 concept using 802.1Q tagging. DevOps use: separate management, production, development traffic on same physical switches.

Q5: How does a service mesh handle mTLS? > Each sidecar (Envoy) receives certificates from the control plane’s CA (Citadel/istiod). When service A calls service B: A’s sidecar → establish TLS with B’s sidecar using service account certificates → verify identity. Neither application knows about TLS — it’s transparent.

Q6: Explain the difference between ClusterIP, NodePort, and LoadBalancer in Kubernetes. > - ClusterIP: Internal-only virtual IP, accessible within cluster. Default. > - NodePort: Exposes service on a static port (30000-32767) on each node’s IP. Accessible from outside. > - LoadBalancer: Creates external cloud LB (AWS ELB, GCP GLB). Routes to NodePort internally. > - Ingress: L7 routing using HTTP host/path rules — single LB for many services.

Q7: What is an Anycast IP? > Same IP address is assigned to multiple servers in different locations. Routing sends traffic to the topologically nearest server. Used by CDNs, DNS (8.8.8.8 routes to nearest Google DNS server), DDoS mitigation.

Q8: TCP connection resets vs FIN — difference? > FIN: Graceful close — one side signals no more data to send. Both sides close independently (4-way). Connection can be half-closed. > RST (Reset): Abrupt close — one party refuses or aborts connection. No waiting. Causes: wrong port, firewall reject, application crash, expired session.

Q9: What is CORS and how do you configure it? > Cross-Origin Resource Sharing — browser security policy preventing JS from one origin making requests to another unless server allows it. Server sends Access-Control-Allow-Origin header.

add_header 'Access-Control-Allow-Origin' 'https://app.example.com';
add_header 'Access-Control-Allow-Methods' 'GET, POST, OPTIONS';
add_header 'Access-Control-Allow-Headers' 'Authorization, Content-Type';

Q10: Explain HTTP/2 improvements over HTTP/1.1. > - Multiplexing: Multiple requests over single TCP connection (no head-of-line blocking) > - Header compression (HPACK): Reduces overhead for repeated headers > - Server push: Server sends resources before client requests them > - Binary protocol: More efficient parsing (not human-readable like HTTP/1.1) > - Stream prioritization: Client can indicate request priority

Q11: How does Kubernetes networking work (CNI)? > Every pod gets unique cluster-wide IP (no NAT). CNI plugin (Flannel, Calico, Cilium) implements: > 1. Creates veth pair for pod → connects to node’s network namespace > 2. Sets up routes so pods can reach each other across nodes > 3. Manages overlay network (VXLAN, IPinIP, BGP) > Calico/Cilium also enforce NetworkPolicy using eBPF/iptables.

Q12: What is eBPF and why is it important for networking? > Extended Berkeley Packet Filter — runs sandboxed programs in the Linux kernel without changing kernel code. Used by Cilium for: > - Zero-overhead pod networking (replaces iptables for kube-proxy) > - Network policy enforcement at kernel level > - Observability (Hubble) > - Load balancing > Faster than iptables at scale (iptables is O(n), eBPF is O(1) with hash maps).

Q13: Describe a scenario where you debugged a network issue in production. > Sample answer structure: > - Symptom: High latency / connection timeouts between service A and B > - Investigation: ss showed high TIME_WAIT count → port exhaustion > - Root cause: Connection pool not reusing connections + high request rate > - Fix: Enabled TCP keepalive + connection pooling + increased ephemeral port range > - Prevention: Added metric for TIME_WAIT count with alerting threshold

Q14: What is MTU and why does it matter for containers/VPNs? > Maximum Transmission Unit — largest packet size for a link (1500 bytes for Ethernet). > VPN/overlay networks add headers → effective MTU shrinks (e.g., VXLAN adds 50 bytes → 1450 MTU). > Misconfigured MTU causes “works for small requests, fails for large” symptoms. > Fix: Set correct MTU on container interfaces, check with ping -M do -s 1472 host.

Q1: What is the difference between git merge and git rebase? > Merge: Creates a merge commit, preserves branch history. Safe for public branches. > Rebase: Rewrites commits on top of another branch. Linear history. Never rebase shared/public branches (changes history = force push needed = breaks others’ work). > Rule: Rebase local feature branches, merge into shared branches.

Q2: What does git reset, git revert, and git checkout do to changes? > git reset: Moves HEAD (and branch pointer). Three modes: > - --soft: Move HEAD only, keep staging + working dir > - --mixed (default): Move HEAD, clear staging, keep working dir > - --hard: Move HEAD, clear staging AND working dir (DESTRUCTIVE) > > git revert: Creates NEW commit that undoes changes. Safe for shared branches. Keeps history. > > git checkout: Switches branches OR restores files. Doesn’t change commit history.

CI/CD — Interview Questions & Answers

Q1: What is GitOps and how does it differ from traditional push-based CD? > Traditional push-based CD: The CI system (Jenkins, GitHub Actions) directly applies changes to the target environment after a build — it pushes Kubernetes manifests or runs Terraform. The CI system needs direct credentials to the cluster or cloud. > > GitOps: Git is the single source of truth for desired state. A controller running inside the cluster (ArgoCD, Flux) watches a Git repository and continuously reconciles actual state to match desired state. The cluster pulls from Git — no inbound credentials needed on the CI side. > > Advantages of GitOps: > - Full audit trail: every change to production is a Git commit with author, timestamp, PR link > - Drift detection: if someone kubectl apply directly, the controller detects and corrects it > - Rollback = git revert — deterministic and auditable > - No external write access to production cluster from CI systems

Q2: Explain DORA metrics. What do they measure and which matters most? > DORA (DevOps Research and Assessment) identified four metrics that predict software delivery performance: > > Deployment Frequency: How often code is deployed to production. Elite: multiple times per day. High: daily/weekly. Medium: weekly-monthly. Low: monthly or less. > > Lead Time for Changes: Time from code committed to running in production. Measures how quickly you can deliver value and fixes. Elite: < 1 hour. High: 1 day - 1 week. > > Change Failure Rate: Percentage of deployments that cause a production failure requiring hotfix, rollback, or remediation. Elite: 0-15%. Low: 46-60%. > > Mean Time to Restore (MTTR): How long it takes to recover from a failure. Elite: < 1 hour. Low: 1 week to 1 month. > > Which matters most: MTTR combined with Change Failure Rate together — you want low failure rate AND fast recovery when failures happen. Deployment frequency is a leading indicator: the more you deploy small changes, the lower your failure rate and faster your recovery.

Q3: What is the difference between Continuous Integration, Continuous Delivery, and Continuous Deployment? > Continuous Integration (CI): Every code change is automatically built and tested. Goal: detect integration failures early. Output: tested artifact (Docker image, JAR, binary). > > Continuous Delivery (CD — delivery): Every successful build can be deployed to production at any time, but a human decides when to push the button. The pipeline prepares and validates the release. The deploy step requires manual approval. > > Continuous Deployment (CD — deployment): Every successful build that passes all automated checks is automatically deployed to production with no human gate. Requires very high confidence in the test suite. > > Most mature engineering teams practice Continuous Delivery with automated canary gates that trigger rollback — functionally close to Continuous Deployment but with safety nets.

Q4: How do you implement zero-downtime deployments in Kubernetes? > Multiple layers required: > > 1. Deployment strategy: RollingUpdate with maxUnavailable: 0 — only scale up new pods before removing old ones. This ensures capacity is never reduced during a rollout. > > 2. Readiness probe: The new pod only receives traffic after its readiness probe passes. A misconfigured or missing readiness probe will route traffic to unready pods. > > 3. PreStop lifecycle hook: Add a preStop sleep of 5-15 seconds. This gives the load balancer time to remove the pod from rotation before SIGTERM is sent. Without this, in-flight requests can be dropped. > > 4. Graceful shutdown: The application must handle SIGTERM and finish processing in-flight requests before exiting. terminationGracePeriodSeconds must be long enough. > > 5. PodDisruptionBudget: Prevents all pods being removed simultaneously during node drains or voluntary disruptions. Set minAvailable: 2 for a 3-replica deployment.

Q5: How do you handle database migrations in a CI/CD pipeline without downtime? > The Expand-Contract pattern (also called parallel change): > > Phase 1 — Expand: Add new schema elements (nullable columns, new tables) without removing anything. Deploy code that writes to both old and new schema. Old schema still works. > > Phase 2 — Migrate: Backfill existing data to new schema in small batches (avoid table locks). Tools: pt-online-schema-change or gh-ost for MySQL, or batched UPDATE loops for Postgres. > > Phase 3 — Contract: Once all data is migrated and code reads only from new schema, remove the old columns/tables in a separate deployment. > > Each phase is a separate deployment, verified before the next. This is why you never do schema changes at the same time as application changes. > > For non-relational changes: Feature flags let you deploy code that uses a new data model without activating it — gradually migrate and enable per-user.

Q6: Walk through how you would design a secure secrets management strategy for a Jenkins pipeline. > Avoid: storing secrets as Jenkins Credentials with static values in the Jenkins config. These are encrypted with the Jenkins master key but don’t rotate and are accessible to anyone with Jenkins admin access. > > Better approach using HashiCorp Vault + JWT auth: > 1. Jenkins job generates a short-lived JWT (role ID + secret ID via AppRole) > 2. Vault authenticates the JWT and issues a short-lived Vault token (TTL: 30 minutes) > 3. Pipeline retrieves only the secrets it needs for this specific job > 4. Secrets are injected as environment variables for the duration of the build only > 5. No secret survives the pipeline; nothing stored in Jenkins > > AWS-native approach: > - Jenkins agent runs with an IAM instance profile > - Agent assumes a per-pipeline IAM role (different permissions per job type) > - Retrieves secrets from AWS Secrets Manager at runtime > - No secret stored in Jenkins at all

Q7: What is a build artifact and why should you build once, deploy many times? > A build artifact is the immutable output of a CI build — a Docker image, a compiled binary, a JAR file, or a zip archive. It is stored in a registry or artifact repository with a unique version identifier (Git SHA, semantic version). > > Build once, deploy many: > - The same artifact that passed tests in staging is promoted to production — not rebuilt > - Rebuilding from source for production could produce a different binary (different dependency versions, different environment) > - The artifact is the unit of trust: security scanning runs against it once, signatures are applied once > - Faster promotions: no rebuild time, just pull and deploy > > Implementation: tag Docker images with Git SHA (ghcr.io/org/app:sha-a1b2c3d), push to registry after CI tests pass, then ArgoCD/Helm references that exact SHA for all subsequent environments.

Q8: How do you handle a broken main branch in a team of 50 engineers? > Immediate actions: > 1. Identify the breaking commit with git bisect or by examining recent CI failures > 2. Revert the specific commit: git revert COMMIT_HASH — creates a new commit, preserves history > 3. Push the revert — pipeline turns green > 4. Post in engineering Slack: “Main was broken by commit X, reverted in Y. Anyone with PRs based on those commits should rebase.” > > Communication: Don’t just silently revert — explain what happened so others don’t build on broken code. > > Longer fix: Author rebases their branch on main (which now includes the revert), fixes the issue properly, re-opens PR. > > Prevention: > - Branch protection rules requiring PR reviews and passing CI before merging > - CODEOWNERS for critical files (requires specific team approval) > - Post-merge CI that re-runs tests after merge to catch integration issues > - Consider trunk-based development with feature flags to reduce long-lived branches

Q9: Explain the differences between GitHub Actions, GitLab CI, and Jenkins. When would you choose each? > GitHub Actions: > - Best for: teams on GitHub, open source projects, greenfield projects > - Pros: native GitHub integration, huge marketplace, OIDC to cloud providers, free for public repos > - Cons: less control over runners, GitHub outage affects CI > > GitLab CI: > - Best for: teams already on GitLab, enterprises wanting all-in-one (SCM + CI + registry + security) > - Pros: excellent built-in security scanning, environments/protected branches, self-hosted option > - Cons: GitLab-specific — harder to migrate away > > Jenkins: > - Best for: complex enterprise pipelines, full control requirements, existing Jenkins investment > - Pros: most flexible and extensible, huge plugin ecosystem, runs anywhere > - Cons: significant maintenance overhead (plugin updates, security patches, shared library management), operational toil > - In 2026: only choose Jenkins if migrating away from an existing Jenkins investment or if compliance requires fully on-prem

Q10: How do you measure and improve your CI/CD pipeline performance? > Key metrics to track: > - Pipeline duration: total time from push to deployed. Continuous Integration (CI)

  • Keeps main branch always buildable
  • Catches integration bugs early

Continuous Delivery (CD)

  • Human approval gate before production deploy
  • Every commit is potentially releasable

  • Every passing build auto-deploys to production
  • No human gate

Docker — Interview Questions & Answers

Q1: What is the difference between a Docker image and a container? > Image: Read-only template with layers. Blueprint. Stored in registry. > Container: Running instance of an image. Has a writable layer on top. Ephemeral (data lost on removal unless using volumes).

Q2: Explain Docker layer caching and how to optimize it. > Each instruction in Dockerfile creates a layer. Cache is invalidated when a layer changes — all subsequent layers rebuild. > Optimization: > 1. Put instructions that change rarely at the top (FROM, RUN apt-get) > 2. Copy dependency files before source code:

COPY requirements.txt .    # cache this layer
RUN pip install -r requirements.txt
COPY . .                   # only invalidates from here
  1. Use --mount=type=cache in BuildKit

Q3: What is a multi-stage build and why is it important? > Allows using multiple FROM instructions. Build artifacts compiled in one stage (with all build tools) are copied to a minimal final image. Result: production image has no build tools = smaller attack surface, faster pull times. > Example: 400MB Go builder → 8MB distroless final image.

Q4: How does Docker networking work? What is the difference between bridge and host networking? > Bridge: Default. Creates virtual network interface on host (docker0). Containers get private IPs, NAT for outbound. Port mapping creates iptables DNAT rules. > Host: Container shares host’s network namespace directly. No NAT, no port mapping needed. Best performance. Security risk — container can see all host interfaces.

Q5: How do you handle secrets in Docker? > DON’T: Bake into image (ENV, COPY of secret files) — visible in image history > DO: > 1. Pass at runtime: docker run -e SECRET=$(vault kv get -field=value secret/myapp) > 2. Docker secrets (Swarm): docker secret create mysecret file → mounted at /run/secrets/ > 3. Build-time secrets with BuildKit: --secret id=npmrc,src=~/.npmrc > 4. Kubernetes secrets / Vault agent sidecar in production

Q6: Container A cannot reach Container B. How do you debug?

# 1. Are they on the same network?
docker inspect A | grep Networks
docker inspect B | grep Networks

# 2. Can A ping B?
docker exec A ping B

# 3. Check port — is B listening?
docker exec B ss -tlnp

# 5. Check container IPs
docker inspect -f '{{.NetworkSettings.IPAddress}}' B

# 6. If different networks, connect to same network:

Q7: How would you reduce a Docker image from 800MB to <100MB? > 1. Use minimal base: FROM node:20-alpine (50MB) vs FROM node:20 (1GB) > 2. Multi-stage build — exclude node_modules from final image if possible > 3. Combine RUN commands to reduce layers > 4. Remove apt cache: rm -rf /var/lib/apt/lists/* > 5. Use --no-install-recommends for apt > 6. Delete build artifacts after compilation > 7. .dockerignore to exclude test files, docs > 8. Consider distroless base

Q8: What is the ENTRYPOINT vs CMD? > ENTRYPOINT: The executable. Not easily overridden (requires --entrypoint flag). > CMD: Default arguments to ENTRYPOINT, easily overridden at runtime.

ENTRYPOINT ["/app/server"]   # always run server
CMD ["--port", "8080"]       # default port, override with: docker run img --port 9090

Exec form ["cmd"] preferred over shell form cmd (no shell wrapping, signals go directly to process).

Q9: How does COPY --from=builder work in multi-stage builds? > Copies files from another named build stage. The builder stage is not included in the final image. You can also copy from external images: COPY --from=gcr.io/distroless/static /busybox /busybox.

Q10: Explain Docker’s restart policies. | Policy | Behavior | |——–|———| | no | Never restart (default) | | always | Always restart, including on daemon start | | on-failure | Restart if exit code non-zero | | unless-stopped | Always restart unless manually stopped | > Use unless-stopped for production services.

Kubernetes — Interview Questions & Answers (Senior Level)

Architecture & Internals

Q1: Walk through what happens when you run kubectl apply -f deployment.yaml.

Step-by-step: 1. kubectl serializes YAML and sends HTTP request to kube-apiserver 2. API server authenticates (certificate, bearer token, OIDC), authorizes (RBAC check) 3. Mutating admission webhooks run first (inject sidecars, set defaults) 4. Object schema validation runs 5. Validating admission webhooks run (OPA/Gatekeeper, PSA) 6. Object persisted to etcd, response returned 7. Deployment controller watches etcd events, detects new/changed Deployment 8. Creates/patches ReplicaSet to match desired state 9. ReplicaSet controller creates Pod objects (no node assigned yet) 10. Scheduler watches for unscheduled Pods, runs filtering + scoring, binds Pod to Node 11. kubelet on selected node watches for bound Pods 12. kubelet calls containerd via CRI, which calls runc to create container 13. kubelet monitors probes, reports status back to API server

Q2: Explain etcd’s role. What happens if etcd goes down?

etcd is the distributed key-value store — the single source of truth for all cluster state. It uses the Raft consensus algorithm, requiring a quorum (majority) of members to function.

  • If etcd goes down: no new resources can be created or updated; existing workloads continue running (kubelet operates independently), but cannot be rescheduled on failure
  • For HA, run 3 or 5 etcd members (tolerates 1 or 2 failures respectively)
  • Backup etcd daily: etcdctl snapshot save
  • Encrypt etcd at rest using EncryptionConfiguration

Q3: What is the difference between liveness, readiness, and startup probes?

Probe Question On Failure Use Case
Readiness Is pod ready for traffic? Removed from Service endpoints App initializing, DB migrations, circuit breaker open
Liveness Is pod still alive? Pod killed + restarted Deadlock, hung goroutine, unrecoverable state
Startup Has app finished starting? Pod killed (if failureThreshold exceeded) Slow-starting apps, prevents premature liveness kills

Critical: Always configure startupProbe for apps with variable startup time. Without it, liveness probe kills the pod before it finishes initializing.

Q4: A pod is stuck in Pending. Walk through your diagnosis.

kubectl describe pod <name> -n <ns>

Events section reveals the root cause:

Event Message Root Cause Fix
Insufficient CPU/memory Requests exceed node capacity Reduce requests, add nodes
No nodes match nodeSelector Label mismatch Check node labels
Taint effect NoSchedule Missing toleration Add toleration
Unbound PersistentVolumeClaim StorageClass issue, no provisioner Check StorageClass, PVC events
Too many pods Node at pod limit (110 default) Scale cluster

Q5: What is CrashLoopBackOff? How do you systematically debug it?

Container repeatedly starts and crashes. Kubernetes adds exponential backoff delay.

Debug steps: 1. kubectl logs <pod> --previous — get last crash logs 2. kubectl describe pod — check Last State exit code 3. Common exit codes: - 1 — application error (check logs) - 137 — OOMKilled (increase memory limit) - 139 — segfault - 143 — graceful shutdown timed out 4. kubectl exec when running briefly — check if config/secrets mounted 5. Override entrypoint to debug: command: ["sleep", "infinity"]

Networking

Q6: How does pod-to-pod networking work across nodes?

Kubernetes networking contract: every pod has a unique routable IP, no NAT between pods.

CNI plugin implements this: - Flannel: VXLAN overlay — encapsulates packets in UDP, sends to destination node’s VTEP, decapsulates - Calico: BGP — advertises pod CIDRs as routes between nodes; no encapsulation = lower overhead; also enforces NetworkPolicy via iptables - Cilium: eBPF-based — replaces iptables entirely, kernel-level enforcement, observability via Hubble

Q7: Explain ClusterIP, NodePort, LoadBalancer, and Ingress differences.

  • ClusterIP: Virtual IP inside cluster only. kube-proxy writes iptables/IPVS rules to DNAT to pod IPs
  • NodePort: Opens same port on every node (30000-32767). External traffic → any NodeIP:port → ClusterIP → pod
  • LoadBalancer: Cloud-provisioned external LB (ELB, GCP LB). Routes → NodePort internally
  • Ingress: L7 HTTP routing. Single external IP/LB, routes by Host header and URL path to different Services. Requires an Ingress Controller (NGINX, Traefik, AWS ALB Ingress)

Q8: How do NetworkPolicies work? What is default behavior?

By default: all pod-to-pod communication is allowed (no isolation).

Once any NetworkPolicy selects a pod, that pod is isolated — only explicitly allowed traffic passes.

# Deny all ingress to app pods, only allow from frontend on port 8080
spec:
  podSelector:
    matchLabels:
      role: backend
  policyTypes: [Ingress]
  ingress:
    - from:
        - podSelector:
            matchLabels:
              role: frontend
      ports:
        - port: 8080

Important: NetworkPolicy is enforced by the CNI plugin. Flannel does NOT enforce it. Use Calico, Cilium, or Weave.

Scheduling & Resources

Q9: Explain Kubernetes QoS classes and their eviction order.

Class Condition Evicted First?
BestEffort No requests or limits set Yes — first killed under pressure
Burstable Requests set but not equal to limits Middle
Guaranteed Requests == Limits for every container Last (never evicted for other pods)

For production pods: aim for Guaranteed QoS. At minimum, always set resource requests.

Q10: What are taints and tolerations?

Taints prevent pods from being scheduled on nodes. Tolerations allow pods to schedule on tainted nodes.

# Taint a node (dedicated GPU node)
kubectl taint nodes gpu-node-1 gpu=true:NoSchedule

# Pod must tolerate to be scheduled here
tolerations:
  - key: gpu
    operator: Equal
    value: "true"
    effect: NoSchedule

Effects: - NoSchedule — don’t schedule new pods without toleration - PreferNoSchedule — try to avoid, not enforced - NoExecute — evict existing pods that don’t tolerate + don’t schedule new ones

Common use: dedicated nodes for monitoring, GPU nodes, spot/preemptible nodes.

Q11: Explain node affinity vs pod affinity vs pod anti-affinity.

  • nodeAffinity: Schedule pods on nodes with specific labels (replace nodeSelector with expressions)
  • podAffinity: Schedule pod on same node/zone as other pods with matching labels (co-location, e.g., cache near app)
  • podAntiAffinity: Schedule pod away from other pods (spread replicas across nodes/zones for HA)
# Spread replicas — never two on same node
affinity:
  podAntiAffinity:
    requiredDuringSchedulingIgnoredDuringExecution:
      - labelSelector:
          matchLabels:
            app: myapp
        topologyKey: kubernetes.io/hostname

Advanced Topics

Q12: What is a Kubernetes Operator pattern?

Extends Kubernetes with domain-specific operational knowledge using: - CRD (Custom Resource Definition) — defines new API types - Controller — watches CRDs + reconciles actual vs desired state

Example: PostgresCluster CRD → Operator handles: provisioning, HA setup, failover, backup scheduling, version upgrades, connection pooling config.

Real operators: Strimzi (Kafka), Zalando Postgres Operator, cert-manager, Prometheus Operator, Argo Rollouts.

Q13: How do you implement zero-downtime deployments in Kubernetes?

  1. Set maxUnavailable: 0 and maxSurge: 1 in rolling update strategy
  2. Configure proper readiness probes (traffic only sent to ready pods)
  3. Add preStop lifecycle hook with sleep to drain in-flight requests
  4. Set terminationGracePeriodSeconds ≥ your max request duration
  5. Use PodDisruptionBudget to prevent voluntary disruptions from taking too many pods
  6. For canary: use Argo Rollouts or Flagger with weighted traffic splitting

Q14: What is IRSA (IAM Roles for Service Accounts) on EKS?

Allows pods to assume AWS IAM roles without static credentials.

How it works: 1. EKS cluster has OIDC provider 2. ServiceAccount annotated with IAM role ARN 3. Pod’s projected service account token is signed by OIDC issuer 4. AWS SDK/CLI exchanges token for temporary credentials via STS AssumeRoleWithWebIdentity 5. Credentials auto-rotate every hour

No more passing AWS keys as environment variables or using node instance profiles.

Q15: How do you debug a pod that keeps getting OOMKilled?

  1. Confirm OOMKilled: kubectl describe pod → check Last State.Reason: OOMKilled
  2. Check current limits vs usage: kubectl top pod <name>
  3. Check if it’s a memory leak or undersized limits
  4. For JVM apps: ensure -XX:MaxRAMPercentage=75 set, not fixed heap size
  5. Temporarily increase limits by 50%, watch if stabilizes
  6. For leak: take heap dump, analyze with MAT or async-profiler
  7. Set up memory usage alerts in Prometheus before OOM

Q16: What is Horizontal Pod Autoscaler and what are KEDA’s advantages?

HPA scales pod count based on CPU/memory metrics (via Metrics Server). Runs every 15s.

KEDA (Kubernetes Event-Driven Autoscaling) extends HPA: - Scale to zero (HPA minimum is 1) - Scale based on external event sources: SQS queue depth, Kafka lag, Prometheus metrics, Redis list length, cron schedules - 50+ built-in scalers

# KEDA ScaledObject — scale on SQS queue depth
spec:
  scaleTargetRef:
    name: worker-deployment
  minReplicaCount: 0        # scale to zero when queue empty
  maxReplicaCount: 50
  triggers:
    - type: aws-sqs-queue
      metadata:
        queueURL: https://sqs.region.amazonaws.com/account/queue
        queueLength: "10"   # target: 10 messages per pod

Q17: How does cert-manager work?

cert-manager is a Kubernetes operator for TLS certificate management.

Flow: 1. Create Certificate or Ingress with cert-manager.io/cluster-issuer annotation 2. cert-manager creates CertificateRequest 3. For Let’s Encrypt: starts ACME challenge (HTTP-01 or DNS-01) 4. HTTP-01: creates temporary Ingress to serve challenge file 5. DNS-01: updates DNS TXT record via provider (Route53, Cloudflare) 6. Let’s Encrypt validates, issues cert 7. cert-manager stores cert in Kubernetes Secret 8. Automatically renews 30 days before expiry

Q18: How do you secure secrets in Kubernetes? (Beyond base64)

Built-in Kubernetes secrets are only base64 encoded — not encrypted by default.

Proper approaches: 1. etcd encryption at rest: EncryptionConfiguration with AES-GCM or KMS provider 2. External Secrets Operator: Syncs from AWS Secrets Manager, Vault, GCP Secret Manager into K8s Secrets 3. HashiCorp Vault Agent Injector: Sidecar injects secrets as files at runtime; never stored in K8s 4. Sealed Secrets (Bitnami): Encrypt secrets with cluster public key, safe to store in Git 5. CSI Secrets Store driver: Mount secrets as volumes from external stores

Best practice: use External Secrets Operator + AWS Secrets Manager for cloud deployments.

Without state, Terraform can’t know what exists vs what to create/update/delete. > Remote state (S3 + DynamoDB locking) is mandatory for teams — prevents concurrent applies that corrupt state.

Q2: What happens during terraform plan? > 1. Reads current state file > 2. Calls provider APIs to refresh real resource state (unless -refresh=false) > 3. Computes diff: desired (config) vs actual (state) > 4. Shows create/update/destroy actions > No changes to real infrastructure. Save plan with -out=tfplan for deterministic apply.

Q3: How do you manage secrets in Terraform? > Never store secrets in .tf files or state. > Options: > - Mark outputs as sensitive = true (hidden in CLI, still in state) > - Use aws_secretsmanager_secret_version data source at runtime > - Pass via env vars: TF_VAR_db_password=$SECRET > - Use Vault provider to read secrets dynamically > - Encrypt state at rest (S3 SSE + DynamoDB encryption)

Q4: Explain terraform import and its limitations. > Brings existing infrastructure under Terraform management by writing its state. > terraform import aws_instance.web i-1234567890abcdef0 > Limitations: only imports state, does NOT generate .tf config. You must write the config manually to match. Use terraform state show after import to see attributes.

Q5: What is the difference between count and for_each? > count: integer, creates indexed list. Removing item in the middle shifts all subsequent indexes → causes destroy/recreate. Good for identical resources. > for_each: map or set, creates named instances. Removing one item only destroys that item. Better for heterogeneous resources with unique identifiers.

Q6: How do you handle Terraform in a CI/CD pipeline? > Pipeline stages: > 1. terraform fmt -check — formatting validation > 2. terraform validate — syntax check > 3. tflint + checkov/tfsec — linting and security scanning > 4. terraform plan -out=tfplan — on PR (post plan as PR comment via atlantis/terraform-github-actions) > 5. terraform apply tfplan — on merge to main, require approval > Use Atlantis or Terraform Cloud for plan/apply workflow with PR integration.

Q7: What is the Terraform lifecycle block? Explain prevent_destroy and ignore_changes. > prevent_destroy: true — block any operation that would destroy this resource. Protects databases, certificates. > ignore_changes = [field] — don’t track drift on specific fields (e.g., ami that gets updated externally, password managed by rotation). > create_before_destroy = true — create replacement before destroying original. Needed for resources that can’t have downtime.

Q8: Ansible is “agentless” — how does it communicate with nodes? > Uses SSH for Linux (paramiko or native ssh binary). Uses WinRM for Windows. No agent installed on managed nodes. > Just needs: SSH access, Python (2.7 or 3.x) on target. > Connection settings: ansible_connection, ansible_user, ansible_ssh_private_key_file > For containers/K8s: uses kubectl or docker connection plugin.

Q9: What is idempotency and how does Ansible achieve it? > Idempotency: running an operation multiple times has the same effect as running it once. > Ansible modules check current state before acting: > - ansible.builtin.file checks if path exists before creating > - ansible.builtin.package checks if package installed before installing > - ansible.builtin.template computes checksum — only copies if content changed > Non-idempotent: ansible.builtin.command and ansible.builtin.shell — use creates or removes args, or check with when.

Q10: How do you structure Terraform for multiple environments (dev/staging/prod)? > Pattern 1 — Workspaces: simple but all envs share same state backend path structure > Pattern 2 — Directory per env (recommended for large orgs):

Q11: Explain Terraform depends_on — when is it necessary? > Terraform infers dependencies automatically from resource references. depends_on is only needed for implicit dependencies not captured in config — e.g., an EC2 instance depends on an IAM policy being attached (but doesn’t reference it in code), or a Helm chart depends on K8s namespace existing via a separate resource. > Overuse of depends_on slows parallelism — only use when necessary.

Q12: How do you handle Terraform state corruption or drift? > Drift detection: terraform plan -refresh-only shows drift without planning changes > State manipulation: > - terraform state list — show all resources > - terraform state show <resource> — inspect resource > - terraform state mv — rename resource (avoid destroy/recreate on refactor) > - terraform state rm <resource> — remove from state without destroying real resource > - terraform force-unlock <lock-id> — release stuck lock (use carefully) > Corruption: restore from S3 versioned backup of tfstate file

Cloud Platforms — Interview Questions & Answers

Q1: Explain the difference between an IAM Role and an IAM User. When should you use each? > IAM User: A permanent identity with long-lived credentials (username/password or access keys). For humans that can’t use SSO, or legacy systems that require static keys. Avoid wherever possible — keys must be rotated, can be leaked, hard to audit at scale. > > IAM Role: A temporary identity assumed by humans, AWS services, or external systems. Credentials are short-lived (15 min to 12 hours), automatically rotated by STS, and scoped to the session. Always use roles for EC2 instances, Lambda, ECS tasks, EKS pods (via IRSA), CI/CD pipelines (via OIDC). > > Rule of thumb: Every non-human identity should use a role. Every human should use SSO/Identity Center federating to roles — never IAM users with long-lived keys.

Q2: What is the difference between a Security Group and a Network ACL in AWS? > Security Groups: > - Stateful — if inbound traffic is allowed, return traffic is automatically allowed > - Attached to ENIs (network interfaces), not subnets > - Allow rules only (no explicit deny possible) > - Evaluated as a single set (all rules checked, most permissive wins) > - Source/destination can be another Security Group (great for service-to-service rules) > > Network ACLs: > - Stateless — must explicitly allow inbound AND outbound for the same connection > - Attached to subnets — affects all resources in the subnet > - Allow and Deny rules — can block a specific IP (Security Groups cannot) > - Rules evaluated in number order, first match wins > > When to use NACLs: Additional perimeter defense, blocking specific IPs/CIDRs, compliance requirements for subnet-level controls. Most teams use only Security Groups for day-to-day; NACLs as a “defense in depth” second layer.

Q3: How does AWS VPC peering work, and what are its limitations? > VPC Peering creates a private network route between two VPCs (same or different accounts/regions). Traffic stays on the AWS backbone — no internet gateway needed. > > Limitations: > - Non-transitive: if VPC A peers with B and B peers with C, A cannot reach C through B. Must create A-C peer separately. > - No overlapping CIDR blocks — peer VPCs cannot have overlapping IP ranges (plan CIDRs centrally) > - No edge-to-edge routing (can’t use a VPC peer as a gateway to the internet or VPN) > > Alternatives for hub-and-spoke at scale: > - AWS Transit Gateway: connects hundreds of VPCs and on-prem networks, supports transitive routing, centralized routing tables, bandwidth up to 50 Gbps per attachment > - AWS PrivateLink: for exposing specific services privately without full VPC peering

Q4: Explain S3 consistency model. What changed in 2020? > Before December 2020: S3 provided eventual consistency for overwrite PUTs and DELETEs. If you wrote to an object and immediately read it, you might get the old version. > > Since December 2020: S3 provides strong read-after-write consistency for all operations — PUTs, DELETEs, LIST. A write followed immediately by a read returns the new data. LIST operations after a PUT show the new object. > > This eliminated many workarounds that applications had to implement. Relevant for: state file storage, data pipelines, distributed coordination patterns built on S3.

Q5: What is an EC2 Instance Profile and how does it differ from directly assigning an IAM role? > An Instance Profile is a container for a single IAM role that can be attached to an EC2 instance. The terms are often used interchangeably, but they are technically distinct: > - IAM Role: the identity with policies attached > - Instance Profile: the mechanism that associates a role with an EC2 instance > > When you create a role for EC2 in the console, AWS automatically creates an Instance Profile with the same name. Via CLI/Terraform, you must create them separately. > > The Instance Metadata Service (IMDS) at 169.254.169.254 serves the temporary credentials to code running on the instance. Applications using the AWS SDK automatically call this endpoint — no credentials configuration needed in the application.

Q6: Compare RDS Multi-AZ vs Read Replicas. When do you need each? > Multi-AZ (High Availability): > - Synchronous replication to a standby in a different AZ > - Standby is NOT accessible for reads — purely for failover > - Automatic failover in 60-120 seconds if primary fails (Aurora: < 30s) > - Use for: production databases where downtime is unacceptable > > Read Replicas (Performance/Scale): > - Asynchronous replication — slight lag (seconds to minutes) > - Replicas are readable — scale out read traffic > - Can be promoted to primary manually (not automatic) > - Up to 15 read replicas for Aurora, 5 for RDS > - Use for: reporting, analytics, read-heavy workloads > > Use both: Multi-AZ for HA, read replicas for scaling reads. Aurora Global Database gives you read replicas across regions with < 1 second replication lag.

Q7: What is AWS Savings Plans and how does it differ from Reserved Instances? > Reserved Instances (RI): > - Commit to a specific instance type, size, region for 1 or 3 years > - Up to 72% savings > - Zonal RI also reserves capacity (important for large instances) > - Scope is specific: m5.xlarge in us-east-1a — changes require Marketplace sale > > Savings Plans: > - Commit to a dollar amount of spend per hour for 1 or 3 years > - Compute Savings Plans: apply to any EC2 family, size, region, OS — even Lambda and Fargate. Most flexible. > - EC2 Savings Plans: specific instance family in a region — deeper discount (~66% max) vs Compute Plans (~66%) > - Cannot sell on Marketplace but automatically apply to matching usage > > When to use: Savings Plans are simpler and more flexible. Use Compute Savings Plans for mixed fleets. Only use RIs if you need capacity reservation guarantees.

Q8: Explain the AWS Shared Responsibility Model in the context of EKS. > AWS manages: the Kubernetes control plane (API server, etcd, scheduler), the underlying EC2 infrastructure for control plane nodes, OS patching of control plane, availability of the K8s API. > > You manage: > - EKS worker node OS updates and AMI patches (use managed node groups with auto-upgrade) > - Kubernetes add-on versions (CoreDNS, kube-proxy, VPC CNI) > - Pod security (SecurityContext, PSA, network policies) > - IAM/RBAC configuration for cluster access > - Container images and their vulnerability patches > - Application-level security, secrets management, data encryption > > With Fargate for EKS: AWS also manages the worker node infrastructure — you only manage pods and their configs.

Q9: How does CloudFront caching work? How do you invalidate cache? > CloudFront caches content at edge locations close to users. When a request arrives: > 1. Edge checks cache: cache hit → serve from edge (fast, no origin cost) > 2. Cache miss → forward to origin (S3, ALB, etc.), cache the response, serve to user > > Cache control is determined by: > - Cache-Control: max-age=3600 header from origin > - CloudFront cache behavior settings (min/max/default TTL) > - Vary header (cache per Accept-Encoding, Accept-Language) > > Invalidation: > - aws cloudfront create-invalidation --distribution-id ID --paths "/index.html" "/static/*" > - Wildcards supported: /* invalidates everything (costs $0.005 per 1000 paths beyond first 1000/month free) > - Better strategy: use versioned filenames (app.v2.js) — old file naturally expires, no invalidation needed > > Cache key customization: Include/exclude query strings, headers, cookies from cache key to control granularity.

Q10: Your EKS pods are failing to pull images from ECR with an auth error at 2am. What’s happening and how do you fix it? > Most likely cause: ECR credentials expired. The ecr get-login-password token is valid for 12 hours. If you’re using a static credential (wrong approach), it expires. > > Correct solution: Use the Amazon ECR credential helper or the VPC ECR endpoint: > - EKS nodes have an instance profile with ecr:GetAuthorizationToken and ecr:BatchGetImage permissions > - The credential-provider plugin in the kubelet config handles token refresh automatically > - Verify with: aws ecr get-authorization-token --region us-east-1 > > Diagnose: > 1. kubectl describe pod FAILING_POD — look at Events section for ErrImagePull / ImagePullBackOff > 2. Check node IAM role has ECR read permissions > 3. Check if ECR is in the same region as the cluster > 4. Verify VPC endpoint for ECR exists (if cluster is in private VPC with no internet) > 5. For cross-account ECR: check ECR repository policy allows the source account’s node role

Monitoring & Observability — Interview Questions & Answers

Q1: What is the difference between monitoring and observability? > Monitoring: Watching predefined metrics and alerting when thresholds are breached. You know what to look for in advance. “Is the system up? Is latency above 200ms?” > Observability: The ability to understand internal system state from external outputs (metrics, logs, traces). You can explore unknown unknowns. A system is observable when you can ask arbitrary questions without deploying new code. > In practice: monitoring tells you something is wrong; observability tells you why.

Q2: Explain the difference between a Prometheus Counter, Gauge, and Histogram. When do you use each? > Counter: Monotonically increasing integer. Reset to 0 on restart. Always use rate() or increase() in queries — never query raw value. > Use for: requests_total, errors_total, bytes_sent_total > > Gauge: Can increase or decrease. Represents a snapshot. > Use for: memory_bytes, active_connections, queue_depth, temperature > > Histogram: Pre-defined buckets. Enables server-side percentile calculation across instances. histogram_quantile(0.99, ...) is accurate when aggregating across replicas. > Use for: request latency, response size — anything you need percentiles for > > Key distinction: use Histogram over Summary when you need to aggregate across multiple instances.

Q3: What is an error budget and how does it influence engineering decisions? > Error budget = 1 - SLO. If SLO is 99.9%, the error budget is 0.1% — about 43.8 minutes/month. > > How it drives behavior: > - Budget remaining → deploy freely, run experiments, take on tech debt > - Budget 50% consumed → be cautious, review risky deployments > - Budget exhausted → freeze all non-critical deployments until next period > > It creates a shared language between product (wants features fast) and engineering (wants reliability). Both sides agree on the acceptable risk level upfront.

Q4: Explain burn rate alerting. Why is it better than threshold-based alerting? > Burn rate = how fast you’re consuming error budget relative to the allowed rate. > A 14.4x burn rate means you’ll exhaust the entire monthly budget in 2 hours. > > Why better than thresholds: > - Threshold alerts: “error rate > 1%” — doesn’t tell you the business impact > - Burn rate: “at this rate, you’ll miss your SLO in 1 hour” — directly tied to user experience > - Reduces noise: short error spikes don’t alert unless sustained > - Multi-window: fast burn (1h window) for critical pages + slow burn (6h window) for warning tickets

Q5: A key service is having intermittent latency spikes. How do you investigate? > 1. Metrics first: Check p99 latency graph over time. Is it all endpoints or specific ones? > 2. Correlate with traffic: Does spike correspond to traffic increase? (saturation) > 3. Check dependencies: Database query time, cache hit rate, external API latency > 4. Traces: Find slow traces during the spike window — identify which span is slow > 5. Logs: Filter logs for high duration_ms during spike — look for patterns > 6. Infrastructure: CPU throttling? GC pauses? Network retransmissions? > 7. Deployments: Any deploys correlate with the spike start? (check annotations on dashboard) > 8. Node-level: kubectl top nodes, check for noisy neighbor

Q6: What is the difference between push and pull metrics collection? > Pull (Prometheus model): Scraper polls targets on a schedule. Centralized config. Easy to see which targets are down (scrape fails). Works well in dynamic environments with service discovery. > > Push (StatsD, Datadog Agent, CloudWatch): Applications push metrics to a collector. Works well for short-lived jobs (Lambda, batch), firewalled environments, or when you can’t open inbound ports. > > Pushgateway bridges the gap: batch jobs push to Pushgateway, Prometheus pulls from it.

Q7: How do you reduce alert fatigue? > 1. Alert on symptoms not causes — alert when user experience degrades, not every CPU spike > 2. Burn rate instead of threshold — sustained problems, not brief spikes > 3. Add for duration — require problem sustained for 2-5 min before alerting > 4. Inhibition rules — suppress warning when critical is already firing > 5. Proper grouping/routing — database alerts go to DB team, not everyone > 6. Review stale alerts — delete or fix any alert that’s been ignored 3+ times > 7. Separate page vs ticket — critical pages on-call, warnings create Jira tickets

Q8: Explain distributed tracing. What problem does it solve? > In a microservices architecture, a single user request touches 10+ services. When a request is slow or fails, traditional logs only show what happened inside each service — you can’t see the full journey. > > Distributed tracing gives each request a unique trace_id. Every service adds a span with timing and metadata. You can visualize the full call graph and immediately see: > - Which service is slow (bottleneck) > - Which dependency call failed > - How much of the total latency is in each service > - How spans are nested (parallel vs sequential calls)

Q9: How does OpenTelemetry differ from Prometheus or Jaeger? > OpenTelemetry is a vendor-neutral instrumentation framework — it defines APIs and SDKs for generating metrics, logs, and traces. It doesn’t store or visualize data. > > Prometheus and Jaeger are backends — they store and query data. > > Workflow: Instrument app with OTel SDK → OTel Collector receives data → forwards to Prometheus (metrics) + Jaeger/Tempo (traces) + Loki (logs). > > Benefit: Change backends without changing application code. Auto-instrumentation for HTTP, gRPC, databases, message queues.

Q10: Production scenario — Grafana shows error rate spiking to 30% but PagerDuty didn’t alert. Why? > Possible reasons: > 1. Alert for duration too long (e.g., for: 15m) — spike resolved before threshold met > 2. Alert expression uses wrong labels — not matching this service’s metric labels > 3. Prometheus scrape failing — metrics stale, alert never evaluates to true > 4. Alertmanager route misconfigured — alert routes to wrong receiver or suppressed > 5. Silence active in Alertmanager > 6. PagerDuty integration broken or routing key expired > > Debug steps: Check Prometheus Alerts tab, check Alertmanager Status page, verify amtool alert query, test fire alert manually.

Q11: What is the cardinality problem in Prometheus? > Cardinality = number of unique time series = unique combinations of label values. > High cardinality kills Prometheus performance because each series needs memory + storage. > > Bad labels (never do this): > - User IDs: {user_id="u_12345"} — millions of series > - Request IDs, URLs with query params > - Timestamps in labels > > Good labels: service, method, status_code, region, environment > > Rule: if a label has > 100 unique values, think carefully. If > 1000, almost always wrong. > High-cardinality data belongs in logs or traces, not metrics.

Q12: What logging strategy do you use for a Kubernetes cluster with 50+ services? > Architecture: > - Fluent Bit as DaemonSet on every node — lightweight, low CPU/memory, reads container logs from /var/log/containers/ > - Enriches with K8s metadata (pod, namespace, deployment, labels) > - Forwards to Loki (cost-efficient) or OpenSearch (rich full-text search) > - Grafana for log exploration + correlation with metrics > > Standards enforced: > - All services output structured JSON logs > - Mandatory fields: timestamp, level, service, trace_id, span_id > - Log correlation: inject trace_id in all logs — click trace in Grafana → jump to Jaeger > - Log retention policy: 30 days hot, archive to S3 Glacier

4. PromQL — Key Patterns

# Requests per second over last 5 minutes
rate(http_requests_total[5m])

# Error rate as percentage
rate(http_requests_total{status=~"5.."}[5m])
  / rate(http_requests_total[5m]) * 100

# 99th percentile latency from histogram
histogram_quantile(0.99,
  sum(rate(http_request_duration_seconds_bucket[5m])) by (le, service)
)

# CPU throttling ratio
rate(container_cpu_cfs_throttled_seconds_total[5m])
  / rate(container_cpu_cfs_periods_total[5m]) * 100

# Memory usage vs limit
container_memory_working_set_bytes
  / container_spec_memory_limit_bytes * 100

# Pods not ready
kube_deployment_spec_replicas
  - kube_deployment_status_ready_replicas

# Top 5 pods by memory
topk(5, container_memory_working_set_bytes{container!=""})

# Alert: sustained high error rate
rate(http_requests_total{code=~"5.."}[5m]) > 0.05
  and on() rate(http_requests_total[5m]) > 10

# Increase in value over 1 hour
increase(errors_total[1h])

# Predict disk fill (4h ahead)
predict_linear(node_filesystem_free_bytes[2h], 4 * 3600) < 0

5. Alerting Rules Best Practices

# Good alert anatomy
- alert: HighErrorRate
  # Expression: must be unambiguous, no false positives
  expr: |
    sum(rate(http_requests_total{status=~"5.."}[5m])) by (service)
    /
    sum(rate(http_requests_total[5m])) by (service)
    * 100 > 5
  # for: ensure it's sustained, not a blip
  for: 2m
  labels:
    severity: critical   # critical / warning / info
    team: platform
  annotations:
    summary: "High error rate on {{ $labels.service }}"
    description: "Error rate {{ printf \"%.1f\" $value }}% for last 2m"
    runbook_url: "https://runbooks.company.com/high-error-rate"
    dashboard_url: "https://grafana.company.com/d/xyz"

Alert Design Principles

  1. Alert on symptoms, not causes — “users can’t check out” not “DB CPU high”
  2. Every alert needs a runbook — on-call should know exactly what to do
  3. Alert on burn rate, not thresholds — SLO-based alerts reduce noise
  4. Avoid alert fatigue — if ignored, it’s useless noise; remove or fix
  5. Test alerts — use amtool to test routes, fire test alerts in staging

6. SLO-Based Alerting

Concepts

SLI (Service Level Indicator) — what you measure
  "ratio of successful requests to total requests"

SLO (Service Level Objective) — your target
  "99.9% of requests complete successfully over 30 days"

Error Budget = 1 - SLO = 0.1% = 43.8 min/month
  When budget is gone → freeze deployments, fix reliability

Burn Rate Alerting (Multi-Window)

Burn Rate = actual error rate / allowed error rate

If SLO = 99.9%:
  Allowed error rate = 0.001 (0.1%)
  If actual = 1%, burn rate = 10x
  At 10x burn rate, budget exhausted in 3 days

Alert thresholds:
  Critical (page): 14.4x burn rate sustained for 1h
    → exhausts 2% of monthly budget in 1 hour
  Warning (ticket): 6x burn rate sustained for 6h
    → exhausts 5% of monthly budget in 6 hours
  Info: 1x burn rate sustained for 3 days
    → on track to exhaust full budget

Error Budget Dashboard Components

  • Remaining error budget % (gauge)
  • Budget burn rate over time (graph)
  • Recent deployments overlaid (annotations)
  • Projected budget exhaustion date

Security & DevSecOps — Interview Questions & Answers

Q1: What is the difference between SAST, DAST, and SCA? > - SAST (Static): Analyzes source code without executing. Runs at commit/CI time. Finds SQL injection patterns, hardcoded secrets, dangerous function calls. Fast, no running app needed. High false positive rate. > - DAST (Dynamic): Tests running application by sending malicious payloads. Finds auth bypasses, XSS, injection that only appears at runtime. Slower, needs deployed environment. > - SCA (Software Composition Analysis): Scans third-party dependencies for known CVEs. Finds “you’re using Log4j 2.14, which has CVE-2021-44228.” Runs at CI time against package manifests. > > A mature DevSecOps pipeline uses all three at different stages.

Q2: How do you prevent secret sprawl in a large organization? > 1. Central secrets management: Vault or AWS Secrets Manager as single source of truth > 2. Eliminate static credentials: Use dynamic secrets (Vault DB engine) and IRSA/Workload Identity > 3. Pre-commit scanning: gitleaks/detect-secrets hook prevents secrets from ever entering VCS > 4. Secret rotation automation: Vault leases or AWS Secrets Manager auto-rotation > 5. Audit trail: Every secret access logged; alert on anomalous access patterns > 6. Break-glass procedure: For emergencies — logged, time-limited, reviewed

Q3: Walk through securing a container from Dockerfile to production. > 1. Dockerfile: Minimal base (distroless/alpine), run as USER 1001, multi-stage build, pin digest not tag > 2. CI scan: Trivy on every build — fail on CRITICAL CVEs > 3. Registry: Private registry, image signing with Cosign, SBOM attached > 4. K8s admission: Kyverno/OPA policy rejects unsigned images or images from untrusted registries > 5. Runtime: Pod security context (readOnlyRootFilesystem, allowPrivilegeEscalation: false, drop all capabilities), NetworkPolicy restricting egress > 6. Runtime monitoring: Falco watching for unexpected process execution, file writes, network connections > 7. Continuous: Weekly re-scans of deployed image digests against updated CVE database

Q4: Explain the principle of least privilege and how you enforce it in AWS + Kubernetes. > Give every identity (user, service, role) only the minimum permissions needed for its function, and nothing more. > > AWS: Start with deny-all. Add only specific actions on specific resources. Use IAM Access Analyzer to find overly permissive policies. Use IRSA instead of node instance profiles (pod-level permissions vs node-level). Use SCPs in AWS Organizations to set organization-wide maximum permissions. > > Kubernetes: Create Role/ClusterRole with specific verbs (get, list, watch) on specific resources. Never use verbs: ["*"]. Service accounts get only what their workload needs. Audit with kubectl auth can-i --list. Disable ServiceAccount token auto-mounting by default.

Q5: What is Log4Shell (CVE-2021-44228)? What would you have done as a DevOps engineer? > Log4Shell was a critical RCE vulnerability in Log4j 2.x. Why Not Environment Variables

Auth Methods (how clients authenticate):

SRE Practices — Interview Questions & Answers

Q1: Explain SLI, SLO, and SLA with concrete examples. > SLI: The metric you measure. “99.2% of checkout API requests completed in < 500ms and returned HTTP < 500 over the last 28 days.” > SLO: Your internal target. “We will maintain 99.5% availability and 99% of requests < 500ms.” > SLA: Your contractual promise to customers. “We guarantee 99% uptime; below this triggers service credits.” > > Relationship: SLA ≤ SLO (internal target must be harder than customer promise to leave buffer). > Setting SLOs: measure user satisfaction, find the threshold below which users complain, set SLO just above that.

Q2: What is an error budget and how does it change team behavior? > Error budget is the maximum allowed unreliability: 1 - SLO. For a 99.9% SLO = 43.8 min/month of allowed downtime. > > Impact on behavior: > - Development teams want to ship fast; SREs want stability. Error budget is the shared arbiter. > - Plenty of budget → deploy, experiment, take risks. Budget is the runway. > - Budget running low → slow down risky changes, prioritize reliability work. > - Budget exhausted → feature freeze until next period; SRE team stops new feature support and focuses on reliability. > > It transforms the conversation from “ops blocking dev” to “both teams share the same budget and make tradeoff decisions together.”

Q3: How do you define SLOs for a new service? > 1. Instrument first: Add the four golden signals metrics before setting targets > 2. Measure baseline: What is current actual availability/latency? > 3. Define good: What does “working correctly for users” mean for this service? > 4. User research: What threshold of degradation causes users to abandon or complain? > 5. Set SLO slightly below baseline: Don’t target perfection — start conservative > 6. Review quarterly: Tighten as reliability improves; loosen if consistently over-achieving > > Common mistake: setting SLOs at 99.99% without measuring whether that’s achievable or even necessary.

Q4: Walk through how you would run a blameless post-mortem. > 1. Timeline building (within 24h): Gather all data — logs, metrics, pager alerts, Slack threads, actions taken. Create objective timeline without assigning fault. > 2. Meeting (48-72h): Invite all involved. IC, engineers, on-call. Facilitator is neutral (often senior SRE not involved in incident). > 3. Focus: What failed? Not who failed. “The process allowed X” not “Alice didn’t do X.” > 4. 5 Whys: Drill to systemic root cause. Usually: missing automation, missing alert, missing test, missing documentation. > 5. Action items: Specific, assigned, time-bound. Not vague like “improve monitoring.” Instead: “Add alert for DB connection pool > 80% — assigned to Bob — due June 1.” > 6. Publish: Share widely. Learning is only valuable when spread.

Q5: What is toil and how do you measure and reduce it? > Toil is manual, repetitive, automatable operational work that scales with service growth and has no lasting value. > > Measuring: Time tracking per task category over 2-4 weeks. Ask: how long did each operational task take this week? > > Reducing: > - Manual DB restarts → health check + auto-restart (livenessProbe or systemd Restart=always) > - Certificate renewals → cert-manager > - Disk fills → alerting at 80% + auto-expansion or cleanup cron > - Manual deploys → CI/CD pipeline > > Goal: < 50% of SRE time on toil. If more, the team is an ops team in SRE clothing.

Q6: How do you design a system for 99.99% availability? > First: understand that 99.99% = 52 minutes/year downtime. This is extremely hard to achieve. > > Requirements: > - Multi-AZ deployment: No single data center failure takes down the service > - Zero-downtime deployments: Rolling updates with maxUnavailable: 0 > - Fast auto-healing: HPA + Cluster Autoscaler, liveness probes with automatic restart > - Fast detection: P99 alert fires in < 2 minutes of degradation > - Fast recovery: MTTR < 10 minutes requires runbooks, automation, practiced incidents > - Database HA: Aurora (sub-30s failover), multi-AZ RDS, read replicas > - Circuit breakers: Prevent cascade failures from one service taking down others > - Chaos testing: Regularly inject failures to find hidden dependencies > > Reality check: Most services don’t need 99.99%. 99.9% (43 min/month) is right for most B2B; 99.5% is fine for many internal tools.

Q7: Explain the difference between MTTR, MTTD, MTTF, and MTBF. > - MTTD (Mean Time to Detect): Avg time from failure occurrence to detection. Goal: minimize with better alerting. Target: < 2 min. > - MTTR (Mean Time to Recover/Repair): Avg time from detection to restoration. Reduced by runbooks, automation, practiced response. Target: < 30 min for SEV-1. > - MTTF (Mean Time to Failure): Avg time a system operates before failing. For hardware/non-repairable items. > - MTBF (Mean Time Between Failures): For repairable systems. MTTF + MTTR. Higher is better. > > Availability formula: MTBF / (MTBF + MTTR) × 100%

Q8: How do you approach on-call rotations and prevent burnout? > Structure: > - Maximum coverage: 1 week primary + 1 week secondary per rotation > - No more than 2 on-call weeks per quarter per person > - Compensation: On-call differential pay, time-off after heavy weeks > > Preventing alert fatigue: > - Review all pages weekly: “should this have paged?” > - Delete or demote alerts that required no action 3 times in a row > - Mean time between pages target: > 2 hours > - Only page when human action is immediately required > > If on-call is miserable: fix the product, not the rotation. Persistent bad on-call = product has fundamental reliability issues.

Q9: What is chaos engineering and how do you introduce it responsibly? > Chaos engineering deliberately injects failures into production (or staging) to discover weaknesses before they cause incidents. > > Responsible introduction: > 1. Start in staging/canary — never directly in production until team is comfortable > 2. Define steady state before experimenting (dashboards ready, team watching) > 3. Start small: kill 1 pod, not the whole deployment > 4. Always have an abort procedure > 5. Run during business hours with team present (not at 3am) > 6. GameDay events: structured, scheduled, everyone informed > > Graduated rollout: > - Week 1: Kill a single pod, confirm auto-restart > - Week 2: Kill all pods in one AZ, confirm multi-AZ failover > - Week 3: Inject 100ms latency to database, confirm circuit breaker > - Month 2: Full region failover test

SRE Practices — Deep Dive Notes

1. What is SRE?

Site Reliability Engineering applies software engineering principles to infrastructure and operations. Coined at Google (2003). Key book: Site Reliability Engineering (free at sre.google).

Core philosophy: - Toil (manual repetitive work) should be < 50% of SRE time - Error budgets balance velocity with reliability - Everything that can be automated should be automated - Post-mortems are blameless — systems, not people, are at fault

SRE vs DevOps: - DevOps: a culture and set of practices - SRE: an implementation of DevOps principles with specific tools (SLOs, error budgets, on-call) - “SRE is what you get when you hire a software engineer to do operations” — Google

2. Service Level Terminology

SLI — Service Level Indicator

A quantitative measure of some aspect of service behavior.

Good SLIs directly measure user experience:

Service Type Example SLI
Request-based % of requests completing successfully in < 500ms
Data pipeline % of records processed without error within SLA window
Storage Proportion of reads returning correct data
Batch job % of jobs completing within scheduled window

Bad SLIs: CPU %, memory usage (these are causes, not symptoms of user pain)

SLO — Service Level Objective

The target value for an SLI.

SLI:  ratio of successful requests (status < 500, latency < 500ms)
SLO:  99.5% over a rolling 28-day window

SLO should reflect user happiness threshold:
  - Below 99% → users notice and are angry
  - 99.5% → acceptable with occasional complaints
  - 99.99% → imperceptible to most users

Setting the right SLO: 1. Start with what users actually experience (measure first) 2. Talk to product/business about acceptable impact 3. Start slightly below measured baseline 4. Tighten only after you can reliably hit the target 5. Avoid over-engineering: 99.999% is almost never necessary

SLA — Service Level Agreement

A contractual commitment to the customer, usually with financial penalties for breach. SLA should be more lenient than SLO (internal buffer).

Internal:  SLO = 99.9%  (what you aim for)
External:  SLA = 99.5%  (what you promise customers)
Buffer:    0.4%         (wiggle room for investigations)

Error Budget

Error Budget = 1 - SLO (as percentage of time)

99.9% SLO:
  Error budget = 0.1% = 43.8 minutes/month downtime

99.5% SLO:
  Error budget = 0.5% = 3.65 hours/month

99.99% SLO:
  Error budget = 0.01% = 4.38 minutes/month

Error budget policy: - Budget > 50% remaining → deploy freely, run experiments, accept risk - Budget 25-50% → slow down risky deployments, investigate reliability issues - Budget < 25% → freeze non-critical deployments, focus on reliability - Budget exhausted → full freeze until next window; SRE team gets priority

3. Toil — Identification and Elimination

What is Toil?

Manual, repetitive, automatable, tactical work that scales linearly with service growth. Not the same as overhead (meetings, reviews) or project work.

Toil characteristics: - Manual (human required) - Repetitive (done over and over) - Automatable (machine could do it) - Reactive (triggered by external event) - No lasting value (same work tomorrow) - Scales with service size

Toil Examples

High Toil:
  - Manually restarting pods when out-of-memory
  - Manual certificate renewals
  - Copying configuration values between environments
  - Manually approving every deployment
  - Manually answering "what's the status of X?" questions
  - Resizing disks when they fill up

Low/No Toil (projects):
  - Building auto-remediation for OOM restarts
  - Implementing cert-manager for automated renewals
  - Building a self-service deployment platform
  - Writing runbooks that prevent manual interventions

Toil Reduction Strategy

1. Measure: Track time spent on each repetitive task
2. Prioritize: Highest frequency × time per instance = biggest ROI
3. Automate first attempt: Script → cron → event-driven
4. Eliminate root cause: Why does the disk keep filling up?
5. Track reduction: Monthly toil hours metric

4. Incident Management

Incident Severity Classification

SEV-1: Complete outage, all users affected, revenue impact
  Example: Payment service down, all transactions failing
  Response: Immediate, full team, external communication

SEV-2: Major feature broken, significant user impact
  Example: Login failures for 40% of users
  Response: < 15 minutes, dedicated IC + responders

SEV-3: Degraded performance, some users affected
  Example: API latency 3x normal, no errors
  Response: < 1 hour, 1-2 engineers

SEV-4: Minor issue, minimal user impact, workaround exists
  Example: Non-critical report generation slow
  Response: Business hours, create ticket

Incident Response Roles

IC (Incident Commander):
  - Coordinates response, not necessarily the one fixing it
  - Manages communications, time-boxes investigation steps
  - Makes escalation decisions
  
Technical Lead:
  - Drives technical investigation and mitigation
  - Reports status to IC every 15 min
  
Communications Lead:
  - Updates status page, internal stakeholders
  - Drafts customer communications
  - Manages exec escalation

Scribe:
  - Documents timeline, decisions, commands run
  - Creates post-mortem skeleton during incident

Incident Communication Template

STATUS:   [Investigating / Identified / Monitoring / Resolved]
SCOPE:    [% users affected, which regions/features]

5. Blameless Post-Mortems

Why Blameless?

When people fear blame, they hide information, minimize their involvement, and don’t tell the full story. This prevents learning. Systems fail, not people.

“If we fire the person who caused the outage, we fire the person who knows most about that failure mode.” — Google SRE

Post-Mortem Structure

1. Incident Summary
   - What happened, impact, duration, severity

2. Timeline (chronological)
   - Detection, key actions, resolution
   - What helped, what slowed us down

3. Root Cause Analysis
   - Use 5 Whys technique
   - Go 5 levels deep: Why did service fail? → Why was DB slow? → Why was query slow? → Why was there no index? → Why wasn't it reviewed?

4. Contributing Factors (not blame)
   - "The runbook didn't mention this failure mode"
   - "Alert fired 10 minutes after user reports began"
   - "No staging equivalent existed for this component"

5. Action Items (specific, assigned, dated)
   - [Owner] [Due Date] Add index on orders.user_id
   - [Owner] [Due Date] Create alert for query > 5s
   - [Owner] [Due Date] Update runbook with new failure mode

   - What we'd do differently

5 Whys Example

Problem: Payment service was down for 22 minutes

  → Database connection pool exhausted

Why 2: Connection pool exhausted
  → Slow queries holding connections

6. Chaos Engineering

Principles of Chaos (Netflix Chaos Monkey origin)

1. Define "steady state" (what does healthy look like)
2. Hypothesize that steady state continues in experimental group
3. Introduce variables: kill pods, inject latency, drain nodes
4. Disprove hypothesis (find weaknesses)
5. Fix weaknesses, repeat

Resilience Patterns

Circuit Breaker:
  CLOSED (normal) → too many failures → OPEN (reject all requests) →
  HALF-OPEN (test one request) → success → CLOSED

Retry with Exponential Backoff:
  Retry after 1s, 2s, 4s, 8s, 16s (max)
  Always add jitter to prevent thundering herd

Bulkhead:
  Isolate failures: separate thread pools or connection pools per dependency
  One slow external API doesn't exhaust all connections

Timeout:
  Always set timeouts on every external call
  Default: 1-5s for synchronous calls; longer for async/batch

Fallback:
  Return cached result, default value, or degraded response when dependency fails
  Example: recommendation service down → return top-selling items

7. Capacity Planning

Capacity Planning Process

1. Measure current utilization
   - CPU, memory, disk, network per service
   - Peak vs average load profiles

2. Forecast growth
   - Historical traffic trends (YoY, QoQ)
   - Business projections (new customer growth, product launches)
   - Seasonal patterns (Black Friday, end-of-quarter)

3. Identify bottlenecks
   - Which resource will hit capacity first?
   - What is the scaling path? (vertical vs horizontal)

4. Plan headroom
   - Run at ~60-70% average capacity (30-40% headroom for spikes)
   - 2x current capacity for HA and rollouts without degradation

5. Automate scaling
   - HPA for pods (CPU/memory/custom metrics)
   - Cluster Autoscaler for nodes
   - KEDA for event-driven scaling

6. Load test
   - Simulate projected peak traffic
   - Find failure modes before users do
   - Validate autoscaling behavior

Round 1: Architecture & Design (45 min)

Q1: System Design

“Design the CI/CD infrastructure for a company deploying 50 microservices 30 times a day to Kubernetes. They have dev/staging/production environments.”

Ideal answer covers:

Clarifying questions to ask first: - Team size? (affects pipeline parallelism needs) - Monorepo or polyrepo? - Kubernetes managed (EKS/GKE) or self-managed? - Any compliance requirements (SOC 2, PCI)? - Current tooling or greenfield?

Architecture decision: - GitOps model: Git is source of truth, ArgoCD pulls desired state - GitHub Actions for CI (build, test, scan, push image) - ArgoCD for CD (sync manifests from Git to cluster) - Separate pipelines per service but shared runner pool

Pipeline flow: 1. Developer pushes → PR created 2. CI: lint → unit test → SAST → build image → Trivy scan → push to ECR with SHA tag 3. CI updates Helm values file in GitOps repo with new image tag 4. ArgoCD auto-syncs staging within minutes 5. Smoke tests run against staging 6. Production promotion: PR to GitOps repo → reviewer approves → ArgoCD syncs production

Environment isolation: - Separate K8s namespaces with RBAC - Separate AWS accounts for production (blast radius containment) - Separate ArgoCD projects with access control

Observability: - Deployment annotations in Grafana → correlate deploys with metric changes - ArgoCD sync status → alert if sync fails or drift detected - DORA metrics tracked: deployment frequency, lead time, MTTR, change failure rate

Q2: Incident Scenario

“At 2am you get paged: ‘checkout is down, all purchases failing.’ You are the IC. Walk me through your response.”

Ideal answer covers:

First 2 minutes: - Open incident channel #inc-20260525-checkout-down - Assign Tech Lead if available, set Comms role - Set severity: SEV-1 (revenue-impacting, all users) - Acknowledge alert to stop repeat pages

Investigate (3-10 min): - Check Grafana dashboard: error rate, latency, traffic drop - kubectl get pods -n production — any CrashLoopBackOff, OOMKilled? - kubectl get events -n production --sort-by=.lastTimestamp - Check recent deployments: ArgoCD history, deployment annotations on dashboard - Check downstream dependencies: payment API, database response times

Mitigation before root cause (10-20 min): - If recent deploy: kubectl rollout undo deploy/checkout -n production — rollback first, investigate later - If database: check connection pool, query times, read replica lag - Scale up if traffic spike: kubectl scale deploy/checkout --replicas=10 - Update status page and stakeholder channel every 10-15 minutes

Recovery confirmation: - Error rate returns to baseline (< 0.1%) - Successful end-to-end checkout test - Monitor for 10 minutes before declaring resolved

Post-incident: - Blameless post-mortem within 48 hours - Action items with owners and due dates - Update runbook with new failure mode

Q3: Trade-offs

“When would you choose Blue-Green over Canary deployment? What about Feature Flags?”

Blue-Green — choose when: - Need instant rollback capability (< 30 seconds, just flip the load balancer) - Stateless services only (sessions don’t cross environments) - Full environment parity required for testing - DB migrations already applied and backwards-compatible - Cost: requires double infrastructure during switch

Canary — choose when: - Need to validate behavior with real production traffic gradually - Can monitor error rate and auto-rollback on threshold breach - Traffic shaping at ingress level (NGINX weighted routing or Argo Rollouts) - More gradual risk: 5% → 25% → 100% - Takes longer but catches issues before full blast radius

Feature Flags — choose when: - Want to decouple deploy from release (deploy the code, turn on the feature separately) - A/B testing different implementations - Emergency kill switch needed (turn off feature without redeploying) - Targeting specific users/cohorts/regions - Dark launching: code in production but feature off for all users

Real answer: Use all three together. Deploy with canary, controlled by feature flags, with blue-green for rollback. The combination gives maximum safety with fine-grained control.

Round 2: Technical Depth (30 min)

Q4: Kubernetes Networking

“Explain exactly what happens when a pod in namespace A calls http://myservice.namespace-b.svc.cluster.local:80.”

Answer: 1. Pod’s DNS resolver (stub resolver) queries 169.254.20.10:53 (or CoreDNS ClusterIP on port 53) 2. CoreDNS looks up myservice.namespace-b.svc.cluster.local 3. CoreDNS returns the Service’s ClusterIP (e.g. 10.96.45.12) 4. Pod initiates TCP connection to 10.96.45.12:80 5. The packet hits iptables/ipvs rules installed by kube-proxy on the source node 6. kube-proxy DNAT rule rewrites destination: 10.96.45.12:80 → one of the pod IPs in the Endpoints list (e.g. 10.244.2.5:8080) 7. Packet is routed to the destination node via the CNI overlay network (VXLAN/BGP depending on CNI) 8. Pod receives the request on its actual IP

What can go wrong: - DNS failure: CoreDNS pod down, or ndots:5 search domain causing excessive DNS queries - Empty Endpoints: pod label selector doesn’t match Service selector - NetworkPolicy blocking: source pod or destination pod has restrictive policy - kube-proxy iptables rules stale: kube-proxy pod crashed or node network issue

Q5: Prometheus Deep Dive

“We have 100 microservices. How do you prevent Prometheus from running out of memory? What is cardinality and how do you control it?”

Answer: Cardinality = total number of unique time series = unique combinations of all label values.

What causes high cardinality: - User IDs, order IDs, session IDs as labels → millions of unique series - URLs with path parameters: /users/12345/orders as a label - Pod names in labels (rotate constantly) - Timestamps or request IDs

Why it’s dangerous: Each unique series requires memory in the TSDB. A Prometheus with 10 million series might need 10-20 GB RAM just for the head block. Series churn (new series created constantly) makes it worse.

Controls: 1. Relabeling rules in Prometheus scrape config: drop high-cardinality labels before ingestion 2. Recording rules: pre-aggregate expensive PromQL expressions, store as lower-cardinality series 3. Metric labels review: enforce label naming standards in code review 4. Cardinality monitoring: alert when a job’s series count exceeds threshold 5. Remote write filtering: use write_relabel_configs to drop before sending to Thanos 6. Tool: mimirtool analyze or Grafana’s Cardinality Management page shows worst offenders

For 100 services: - Federated Prometheus: one Prometheus per namespace/team, global Prometheus scrapes aggregated metrics only - Or: Thanos/Cortex/Mimir for horizontally scalable storage — multiple Prometheus instances, Thanos Querier provides global view

Q6: Security

“A developer accidentally committed an AWS secret key to the public GitHub repo 2 hours ago. What do you do?”

Immediate (minutes): 1. Rotate the key immediately — AWS console → IAM → Security credentials → make inactive + delete 2. Create a new access key if the service still needs it (or switch to IRSA/role-based) 3. Check CloudTrail for API calls with the compromised key in the last 2 hours 4. Look for: unusual regions, new IAM users created, new EC2 instances, S3 data access/exfiltration

Clean up Git history: 5. git filter-repo (preferred) or BFG Repo-Cleaner to remove secret from all history 6. Force-push to overwrite remote history (coordinate with team — they need to re-clone) 7. GitHub has a secret scanning feature that may have already flagged it — check security alerts

Communicate: 8. Notify security team per incident process 9. Document: what was exposed, what was accessed, what was done 10. If customer data was accessible: legal/compliance review for breach notification

Prevent recurrence: 11. Enable GitHub Secret Scanning and push protection (blocks commits with secrets) 12. Add gitleaks as pre-commit hook for all developers 13. Eliminate static credentials entirely: switch to IRSA for EC2/EKS, OIDC for CI/CD

Design 1: Production CI/CD Platform for 200 Engineers

Clarify

  • Team size: 200 engineers, 50+ microservices
  • Deployment frequency target: 50+ deploys/day
  • Current state: manual, Jenkins on-prem
  • Requirements: self-service, secure, fast feedback

High-Level Architecture

Developer pushes to Git
        ↓
GitHub / GitLab (source control)
        ↓
CI Platform (GitHub Actions or GitLab CI)
  ├── Lint + Test (parallel, per-service)
  ├── Security scanning (SAST, SCA, container scan)
  ├── Build + Push to registry
  └── Trigger CD
        ↓
ArgoCD (GitOps CD layer)
  ├── Staging sync (automatic, on merge to develop)
  ├── Production sync (manual approval or scheduled)
  └── Drift detection + auto-remediation
        ↓
Kubernetes clusters (staging + production, multi-AZ)
        ↓
Monitoring + Alerting → Slack + PagerDuty

Key Design Decisions

Why ArgoCD over push-based CD? - Pull model: cluster pulls from Git, no need to grant CI outbound access to K8s - Git is the single source of truth — every cluster state is auditable - Drift detection: if someone kubectl apply directly, ArgoCD detects and corrects - Multi-cluster support: one ArgoCD instance managing many clusters

Scaling CI runners - GitHub Actions self-hosted runners on K8s (ARC — Actions Runner Controller) - Runners auto-scale based on queue depth - Spot instances for cost (stateless, OK to be interrupted) - Caching strategy: Docker layer cache in ECR, pip/npm cache in S3

Deployment strategies per risk level - Internal tools: Direct rolling update - Customer-facing: Canary → 5% → 25% → 100% with automated rollback on error rate - DB migrations: Feature flags + backwards-compatible migrations first, code second

Security gates - Every build: SAST, SCA, container scan — fail on CRITICAL - Image signing: Cosign with OIDC, Kyverno enforces at admission - Secrets: Never in CI env vars — pull from Vault/Secrets Manager

Design 2: Multi-Region Kubernetes Platform

Clarify

  • Active-active or active-passive across regions?
  • RTO/RPO requirements?
  • Stateful workloads?
  • Data residency requirements (GDPR)?

Architecture

                   Route53 (Latency-based routing)
                       /              \
              us-east-1               eu-west-1
            EKS Cluster             EKS Cluster

                  │                       │
        RDS Aurora              RDS Aurora

Single-Region vs Multi-Region Decision Tree

Traffic regional distribution matters?  → Multi-region latency-routing
Compliance (GDPR, data sovereignty)?    → Multi-region required
99.99%+ SLO required?                  → Multi-region or multi-AZ + fast failover
Team < 20 engineers?                   → Multi-AZ is enough, multi-region is operationally complex
Cost budget limited?                   → Multi-AZ with DR plan

Key Tradeoffs

  • Active-Active: Higher complexity, data consistency challenges (distributed writes), higher cost, true zero-downtime failover
  • Active-Passive (warm standby): Simpler, some downtime during failover (minutes), RDS Aurora failover < 30s

Design 3: Observability Platform for 100+ Services

Scale Requirements

  • 100 services, each emitting metrics, logs, traces
  • ~50,000 metrics/min ingestion rate
  • Log volume: 50GB/day
  • Trace sampling: 1% of requests with 100% of errors

Architecture

Applications (OTel SDK)
        ↓
OTel Collector (DaemonSet) — receives, filters, batches
    ├── Metrics → Prometheus → Thanos (long-term, S3-backed)
    ├── Logs → Fluent Bit → Loki (index-free, S3-backed)
    └── Traces → Tempo (S3-backed)
        ↓
Grafana (single pane of glass)
  - Unified dashboards
  - Log ↔ Trace ↔ Metric correlation
  - SLO dashboards with burn rate

Alerting:
Prometheus rules → Alertmanager → PagerDuty + Slack
Grafana alerts for business metrics

Key Decisions

Why Thanos over just Prometheus? - Prometheus stores data locally — limited retention, no HA - Thanos: S3 object storage → unlimited retention at low cost - Query federation across multiple Prometheus instances - Global view across clusters from single query endpoint

Why Loki over Elasticsearch? - Loki indexes only labels, not full text → 10-30x cheaper storage - At 50GB/day: Elasticsearch ~$500/mo vs Loki ~$50/mo - Tradeoff: Full-text regex search slower vs indexed Elasticsearch - Acceptable when logs are well-structured JSON with good labels

Cardinality control - High-cardinality labels (user_id, request_id) belong in traces/logs, NOT metrics - Recording rules for frequently-queried heavy expressions - Drop irrelevant metrics at collector level (reduce by 40-60%)

Design 4: Zero-Downtime Deployment Strategy

Question

“How would you design deployment pipelines for an e-commerce site that cannot tolerate downtime?”

Strategy Matrix

Risk Level | Strategy           | Rollback Time | Notes
──────────────────────────────────────────────────────────────
Low risk   | Rolling Update     | 5-10 min      | maxUnavailable: 0
Medium     | Blue-Green         | < 1 min       | Switch LB target group
High       | Canary             | < 1 min       | Automated on error rate spike
DB changes | Expand-Contract    | N/A           | Multi-step: add → migrate → remove
Hotfix     | Feature Flag off   | Seconds       | Kill switch without deploy

Canary Deployment Flow

v1 (100%) running in production
      ↓ Deploy v2 to canary (5% traffic via weighted routing)
      ↓ Monitor for 10 minutes:
        - Error rate < baseline + 0.5%
        - P99 latency < baseline + 50ms
      ↓ Pass → promote to 25% → 50% → 100%
      ↓ Fail → automatic rollback to 100% v1 (< 60 seconds)

Database Migration Pattern (Expand-Contract)

Problem: ALTER TABLE on 100M row table = 30min lock = unacceptable downtime

Solution — 3 phases:
  Phase 1 (Expand):
    - Add new column (nullable, no constraint)
    - Deploy code that writes to BOTH old and new column
    - Backfill old rows in batches (pt-online-schema-change or gh-ost)
    
  Phase 2 (Migrate):
    - Deploy code that reads from new column, writes to both
    - Add NOT NULL constraint after backfill complete
    
  Phase 3 (Contract):
    - Deploy code that only uses new column
    - Drop old column
    
Each phase: separate deployment, verified working before next

Design 5: Secrets Management at Scale

Question

“Design a secrets management system for 50 services across 3 environments.”

Architecture

HashiCorp Vault (HA — 3 nodes + Raft storage)
    │
    ├── Auth: Kubernetes OIDC per cluster
    ├── Auth: AWS IAM for EC2/Lambda
    ├── Auth: AppRole for CI systems
    │
    ├── KV v2: Static secrets (API keys, certs)
    ├── Database: Dynamic credentials for each service
    │       └── Postgres short-lived creds (TTL: 1hr)
    └── PKI: Internal TLS certificates
    
Access pattern (K8s):
  ServiceAccount → OIDC token → Vault token → read secret
  Vault Agent sidecar → file injection into pod
  OR: External Secrets Operator → K8s Secret (encrypted etcd)
  
Access pattern (CI/CD):
  GitHub Actions → OIDC → Vault AppRole → secret at runtime
  Never stored in GitHub env vars

Key Principles

  1. Never store secrets in Git, CI config, or container images
  2. Use dynamic secrets over static — auto-expiring DB creds eliminate revocation problem
  3. Least privilege per service — each service gets its own Vault policy
  4. Audit everything — every secret read logged with service identity
  5. Auto-rotation — static secrets rotate automatically via Vault leases
  6. Break-glass — emergency access procedure: logged, time-limited, requires two approvals

Common Design Anti-Patterns to Avoid

Anti-Pattern Why it’s Bad Better Approach
Single region, single AZ SPOF Multi-AZ minimum
Static long-lived credentials Can’t be rotated if leaked Dynamic secrets / IRSA
All-in-one monolith CI/CD Blast radius too large Per-team or per-service pipelines
